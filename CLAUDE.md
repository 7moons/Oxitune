# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Oscilla is a desktop client for YouTube Music built on **Tauri v2** (Rust backend) + **TypeScript** (frontend, no framework). It works by opening `https://music.youtube.com` in a Tauri webview and injecting a bundled script (`src-tauri/inject/preload.js`) that manipulates the page's DOM directly — there is no React/Vue/etc., and no server-side rendering of YouTube Music itself. Companion windows (settings, mini player, local library, room sync) are separate first-party HTML pages built by Vite.

**Name:** the app is **Oscilla** (formerly YTMD). User-visible text says Oscilla (Polish declines it: Oscilli, Oscillę, Oscillą). Deliberately still `ytmd`: the Tauri `identifier` `com.ytmd.desktop` (WebView data, i.e. the YouTube sign-in, window state and the single-instance lock live under it), internal identifiers (`ytmd_bridge`, `ytmd-*` CSS/events, `__ytmdDefinePlugin`, the plugin API's `ytmd` object and `app.ytmd.*` plugin ids, which installed plugins depend on), protocol constants (HKDF labels, the `ytmd-settings` backup tag) and the old names the migration code recognizes (`~/.ytmd`, `ytmd://`, `YTMD-` codes, the `YTMD` install/login item). `config::app_dir_in` moves `~/.ytmd` to `~/.oscilla` once; `src-tauri/windows/hooks.nsh` removes an old YTMD install on Windows; deb/rpm replace the `ytmd` package.

## Commands

```bash
bun install                # install deps (Bun is the primary package manager/runtime)

bun run tauri dev          # dev mode: builds preload.js then launches the Tauri app
bun run tauri build        # production build -> src-tauri/target/release/bundle/ (.deb/.rpm/.AppImage)

bun run build:preload      # bundle src/preload/index.ts -> src-tauri/inject/preload.js (must rerun after preload edits before `cargo build`/`cargo test` for it to affect a real run)
bun run build              # tsc + vite build (companion windows) + build:remote + build:preload
bun run build:remote       # phone remote app (remote.html + src/remote/) -> dist-remote/, embedded into the binary
bun run typecheck          # tsc --noEmit, no build output

bun test                   # all frontend tests (src/tests/*.test.ts, bun:test runner)
bun test src/tests/dsp.test.ts   # single file
bun test -t "test name"          # single test by name

cd src-tauri
cargo test                 # all Rust tests (inline #[cfg(test)] mod tests in each source file)
cargo test sync_room::      # tests in one module
cargo test test_name        # single test by name substring
cargo clippy                # lint — keep this clean, it's enforced as part of doing the job right
cargo check                 # fast compile check without lint
```

There is no frontend linter/formatter configured (no ESLint/Prettier) — `tsc --noEmit` with `strict`, `noUnusedLocals`, `noUnusedParameters` is the only frontend gate. Keep code free of `any` — the codebase has none; `window.__TAURI__` is fully typed in `src/types/global.d.ts`, use that instead of re-casting `window as any`.

Linux system deps needed to build (`webkit2gtk-4.1`, `libappindicator-gtk3`, `librsvg2`, `libasound2-dev`) are listed per-distro in README.md.

## Architecture

### Two frontends, two build outputs
- **The injected script** (`src/preload/index.ts` and everything it imports — `src/plugins/*`, `src/preload/bridge.ts`, `src/preload/observer.ts`) is bundled by `bun build` (via `build:preload`) into a single file, `src-tauri/inject/preload.js`, **as an IIFE** (`--format iife`): it runs as a classic script in YTM's own global scope, so an unwrapped bundle turns every minified top-level name into a page global (the guest flag once became `window.yt = true` and wiped YouTube's `yt.*` namespace); `src/tests/preload_bundle.test.ts` fails if the bundle declares any global. That file is embedded into the Rust binary at compile time with `include_str!("../inject/preload.js")` in `src-tauri/src/lib.rs` and handed to Tauri as `initialization_script(...)` for the main window, which loads the *external* URL `https://music.youtube.com`. **If you edit anything under `src/preload/` or `src/plugins/`, you must run `bun run build:preload` before the Rust app will reflect the change** — `cargo build`/`cargo tauri dev` do not do this for you automatically outside of the `bun run tauri dev` script.
- **Companion windows** (`index.html`, `settings.html`, `local.html`, `miniplayer.html`, `sync.html` + their `src/ui/*.ts` scripts) are ordinary Vite multi-entry pages (see `vite.config.ts`), served as local Tauri windows, not injected into an external page.

### Plugin system (`src/plugins/`)
Each plugin is a **singleton object literal** implementing `YTMDPlugin` (`src/plugins/types.ts`): `id`, lifecycle hooks `onInit`/`onTrackChange`/`onPlaybackChange`/`onTick`/`onDestroy`, each receiving a shared `PluginContext` (current track, config, `invoke`, `sendPlayerCommand`, `getVideoElement`). `PluginRegistry` (`src/plugins/registry.ts`) registers all plugins once in `src/preload/index.ts`, and calls each hook by name (`plugin.onInit(ctx)`), catching and logging per-plugin errors so one broken plugin doesn't take down the others.

Because each plugin module is registered exactly once, per-plugin private state (cleanup callbacks, cached controllers, etc.) lives in **module-level `let` variables**, not on `this` — e.g. `src/plugins/volume/index.ts` declares `let cleanup: (() => void) | null = null;` at module scope and sets/reads it from the lifecycle hooks. Follow this pattern for new plugins; do not stash state on `this`.

Plugins interact with the live YouTube Music page purely through DOM queries/mutation and the `video` element (`ctx.getVideoElement()`), since there is no access to YouTube Music's internal JS state. `PlayerObserver` (`src/preload/observer.ts`) is the single source of truth for track/playback-change/tick events, driven by `MutationObserver` + polling; `PlayerBridge` (`src/preload/bridge.ts`) is the write side (play/pause/seek/volume/etc. via native player-bar button clicks or the `video` element directly).

### Two separate IPC paths — this is the part most likely to surprise you
1. **Companion windows → Rust**: standard Tauri IPC, `window.__TAURI__.core.invoke('command_name', args)` / `.event.listen(...)`, handled by `#[tauri::command]` functions in `src-tauri/src/commands.rs`, registered in the top-level `.invoke_handler(tauri::generate_handler![...])` in `src-tauri/src/lib.rs`. Each window has its own capability file (`src-tauri/capabilities/<window>.json`) listing only the commands it uses.
2. **Injected script (music.youtube.com) → Rust**: the main window shows an *external* origin shared with YouTube's own scripts, so it gets its own capability (`capabilities/main.json`, window `main`, remote URL `https://music.youtube.com/*`) allowing exactly two app commands and **no events**: `ytmd_bridge { cmd, args }` (`invokeBackend()` in `src/preload/bridgeClient.ts`) runs one entry of the `bridge_commands!` table in `src-tauri/src/bridge.rs` and answers the invoke directly; `ytmd_subscribe { channel }` hands Rust a Tauri `Channel` on which `page_ipc.rs` relays only the app events listed in `PAGE_EVENTS` (`pageEvents.listen()` in the page), projected so the page never sees the room code, paths or the remote token (`page_config`, `page_room_value`). The table is the minimum a player page needs: no files, downloads, whole-config read/write, room admin, remote token or updater (a Rust test lists what must never be in it), and every entry validates its input. `build.rs` declares an ACL app manifest, so *every* app command needs an `allow-<command>` permission in the calling window's capability file — add new commands to `APP_COMMANDS` there, to `generate_handler!` in `lib.rs` and to the one window capability that needs them. `src/tests/sync.test.ts` fails if any `invoke('x')`/`invokeBackend('x')`/`runAction('x')` under `src/preload`/`src/plugins` isn't in the bridge table, and checks the capability files (only `main-page` is remote; no `"*"` windows).

`get_current_track` (reads `AppState.current_track`, written by `update_track_info`) lets a companion window opened mid-song fetch what's already playing instead of waiting for the next periodic `track-changed` broadcast (which only fires on track/playback change or every ~15s while playing).

### Companion windows are created on demand
`tauri.conf.json` declares no windows. The main window is built in `lib.rs` (with `nav_policy.rs` deciding where it may navigate and what opens in the browser, and `connectivity.rs` swapping in `offline.html` when YTM can't be reached); the companion windows (`miniplayer`, `settings`, `local`, `sync`) are created by `windows.rs` when first opened. `settings` and `local` are destroyed on close (each is a separate ~70 MB web process); `miniplayer` and `sync` hide. All are `decorations(false)`, so `data-tauri-drag-region` is the *only* way to move them, and that is inert unless `core:window:allow-start-dragging` is in the window's capability file (it is not part of `core:window:default`). If dragging silently stops working after a capabilities edit, check that first. The main window is undecorated too (`.decorations(false)` in `lib.rs`): YTM's nav bar is its title bar, and `src/preload/ui/windowControls.ts` pins minimize/maximize/close to the window's top-right corner (YTM's right-hand nav buttons give up their 100px edge gap for them, via a stylesheet rule) and drags the window from a document-level `mousedown` on the bar's empty space (never by setting attributes on YTM's elements). The page has no window permissions, so these go through the bridge's `window_*` commands (main window only); close goes through `CloseRequested`, so close-to-tray still applies.

### Installed plugins (runtime, `src-tauri/src/plugins/`)
Besides the built-ins, users install plugins from the built-in official registry (`registry::official()`, key in `OFFICIAL_KEY`; hideable), registries they add, or, in developer mode, from a folder. `docs/PLUGIN_API.md` is the contract. `manifest.rs` validates manifests (closed permission set; `internal:*` only for built-ins), `registry.rs` fetches a registry's `index.json` + minisign signature (`minisign-verify`, the registry's key) and checks archive sha256, `archive.rs` extracts `.tar.gz` into a staging dir (no absolute paths, `..`, links or special files) and renames it into `~/.oscilla/plugins/<id>` atomically. Each enabled plugin becomes its own initialization script calling `__ytmdDefinePlugin` (`src/preload/pluginHost.ts`), which gives its code a frozen `ytmd` object with only the granted groups; storage and network (`plugin_storage_*`, `plugin_fetch`, manifest `hosts` only) are re-checked in Rust. Errors are reported through `plugin_error`; 5 switch a plugin off. Enabling, installing or updating needs a restart (`restart_app`); there is no hot reload. Built-ins also have `manifest.json`s (`app.ytmd.*`) and get a `PluginContext` scoped to their permissions (`scopedContext` in `registry.ts`); `src/tests/plugins.test.ts` fails if a built-in calls a command or listens to an event its permissions don't cover. The ad blocker, SponsorBlock and the downloader are not in the core: they live in `_plugins-export/` (the official registry repo `oscilla-plugins`, ready to push). The downloader works through the `media:save` permission (`plugins/media_save.rs`): the add-on passes only a video id and a format from `FORMATS`, the core runs yt-dlp with the fixed `ytdlp_args` into `PluginState::media_dir`. yt-dlp/ffmpeg are the system's or ours: `plugins/media_tools.rs` installs them into `~/.oscilla/tools/` only after consent (a native dialog Oscilla shows for `plugin_media_install_tools`, or Settings' button), from GitHub releases only, checked against each release's published SHA-256 file, copying just `ffmpeg`/`ffprobe` out of the archive under fixed names, and refreshes its yt-dlp weekly; and reports `plugin-media-progress` with file names only; `cargo test real_ytdlp -- --ignored` checks that command line against a real yt-dlp. A test fails if `_plugins-export`'s manifests stop passing this core's checks or `minisign.pub` stops matching `OFFICIAL_KEY`.

### Rust backend module map (`src-tauri/src/`)
One file per concern, each owning its own state and (mostly) its own inline tests: `config.rs` (persistent `~/.oscilla/config.json`, with legacy-path migration from `~/.config/ytmd/config.json`), `mpris.rs` (Linux D-Bus media keys), `discord_rpc.rs` (native Discord IPC socket; a `watch`-channel loop that only ever sends the latest presence, at most 5 per 20 s since Discord silently drops the rest, skips repeats within 2 s of timestamp jitter, clears it when there's no title or after `discord_clear_after_pause_min` paused, and derives the start time from the page's `sampled_at_ms`), `session.rs` (resume on launch: the last song id, playlist and position go to `~/.oscilla/session.json`, not the config, written at most every 5 s plus on window close and exit; at startup the main window opens `watch?v=…&list=…` instead of the home page unless the session is older than 30 days, within 5 s of the song's end, `resume_on_launch` is off, or the launch came from an `oscilla://` (or older `ytmd://`) link, and `src/preload/resume.ts` mutes YTM's autoplay, seeks, then pauses unless `resume_autoplay`; the target is handed out once by `take_resume_session`, so a reload never seeks again), `tray.rs`, `shortcuts.rs` (global shortcuts), `local_files.rs` (local library scan, cached by mtime/size, off the main thread), `remote_server.rs` (phone remote: axum HTTP + WebSocket on the LAN, see "Phone remote" below), `power_manager.rs` (sleep inhibition: `systemd-inhibit` on Linux, `SetThreadExecutionState` on a holder thread on Windows), `screen_lock.rs` (pauses on the desktop's real lock signal when `pause_on_lock` is on: D-Bus on Linux, session-state polling via `WTSQuerySessionInformationW` on Windows; never infer a lock from `document.hidden`, which is also true when minimized). Windows-only code is compiled only by the `backend-windows` CI job, so check it there after touching it, and the room-sync pair `sync_room.rs` (room/member state, `WireMessage` protocol, LAN UDP-beacon + TCP transport) + `p2p_sync.rs` (libp2p/DHT internet transport, added as an alternate transport for the *same* `WireMessage` protocol — see `plan.md` for the full design rationale if extending this). Roles (`MemberRole`: host, moderator, DJ, listener) live in the host's `RoomState`; the host checks every guest `Control`/`Moderate` against them, listeners' controls are dropped, and a kick bans the guest's install-wide Ed25519 identity (`~/.oscilla/sync_identity`, 0600; `client_hash` = SHA-256 of its public key), so rejoining under a new member id is refused with `Rejected`. The internet path hosts on every public broker at once and guests try them in parallel: picking "the first broker that answers" on each side separately left slower guests on a different broker than the host. All room traffic (LAN lines, LAN beacon, MQTT payloads) is sealed by `sync_crypto.rs` (protocol 3: `OSC-` + 26-char codes = 130 bits; AES-256-GCM key and public topic id HKDF-SHA256-derived from the code via `ring`; every message is a signed envelope `{v, from, sid, ctr, ts, msg}` checked against the sender's key with a replay window; the host's key is pinned after the first join). v2 peers are recognized only to answer `Rejected{Outdated}` (`LegacyCipher`). Never write crypto primitives by hand, and bump the protocol version with a readable message for older clients on any wire change. Bans, approvals and remembered roles are keyed by `client_hash`. Room features on top of membership (join approval, vote skip, reactions, the shared queue, the handoff snapshot) live in `sync_room/features.rs`. When the host leaves it broadcasts `HostHandoff` to `pick_successor` (highest role, then earliest join) and stops; that member re-hosts the same code via `resume_room` and everyone else runs `reconnect`; if the host just vanishes, the same successor takes over only after the room is not found while a broker was reachable (a guest whose own network dropped must not fork the room). `end_room` is the only thing that closes a room for everyone. A host can show a "Listen along" button on Discord (`set_discord_invite`, `join_link.rs`): it links to `pages/join/index.html` (GitHub Pages, `.github/workflows/pages.yml`) with the room code only after `#`, since the code is the room key; turning it on forces join approval, turning approval off drops it, and it applies only to the room it was turned on for. That page opens `oscilla://join/<code>` (`tauri-plugin-deep-link`, forwarded by single-instance), which only fills in the code in the Listen Together window; the user still presses Join. In a room, `src/plugins/sync-room/queuePanel.ts` turns YTM's "Up next" tab into the shared queue: the tab is relabeled and its `#tab-renderer` hidden purely through an injected stylesheet keyed on attributes on `<html>`, our panel is inserted into `#side-panel` (re-mounted by a poll), and clicks on YTM's own "Add to queue"/"Play next" menu items (`queueAddEndpoint` in the item's `data`, only read) are stopped in the capture phase and sent to the shared queue instead. In a room the host's player is the only one that acts: a guest's player-bar clicks, media keys and picked songs become `WireMessage::Control` requests (`send_sync_control` → `sync-control-remote` on the host), and guest-side auto-seekers (crossfade, skip silence, SponsorBlock) stand down via `src/preload/syncRole.ts`. Guests close small drift by nudging `playbackRate` (seek only past 2s) and estimate transit from the smallest recent `now - timestamp_ms`, never trusting the host's wall clock. Song id and position on both sides come from `#movie_player`'s `getVideoData()`/`getCurrentTime()` (URL `v` and `video.currentTime` switch at different moments around a track change); at a song's end the host stays silent while `video.ended`, and a guest that finished first pauses and waits for the host's next song instead of going back (else YTM's own autoplay makes it flip between songs). `tauri-plugin-single-instance` (first plugin in `lib.rs`) makes a second launch just bring the running window back. Logging goes through `tauri-plugin-log` to `~/.oscilla/logs` (rotated, local time); there is no `env_logger`. The injected page's console is lost when the app closes, so what the page decides or sees going wrong goes to the same file through `pageLog()`/`playerSnapshot()` (`src/preload/diagLog.ts` → the `page_log` bridge command → `page_log.rs`, which rate-limits and cleans each line since any script in the page can call it); use that, not `console.error`, for anything worth finding later. Global shortcuts are configurable (`AppConfig::shortcuts`, one accelerator per action in `shortcuts::ACTIONS`, whose names must be the page's `handlePlayerCommand` commands; a test checks that) and change only through the `set_shortcut`/`reset_shortcuts` commands, which re-register them. Custom equalizer presets live in `AppConfig::equalizer_custom_presets` (ids `user-…`, sanitized in `config.rs`). All backend state is centralized in `AppState` (`lib.rs`), constructed once and shared via `Arc<AppState>` / `tauri::State`.

### Lyrics (`src-tauri/src/lyrics/`)
The backend owns lyrics; the page, the miniplayer and the phone remote only display them. Providers (`local` .lrc/tag lyrics from the library folder, `lrcred` = lrc.red's word-timed TTML, `lrclib`, `unison` = Better Lyrics' community lyrics per video, `musixmatch`, `netease`, `ytm` = the text YTM's own Lyrics tab shows, handed over by the page as `ytmPlain`, `genius`) run in parallel, 6 s each; the first provider in `AppConfig::lyrics_providers` order with synced lyrics wins, else the first with plain text (`decide()`). Unison, Musixmatch and NetEase are unofficial for us and off by default. A provider added in a newer version joins a saved list at its place in the default order (`sanitize_provider_settings`, mirrored by `normalizeProviders`), not at the end, or a new word-by-word source would never be picked. TTML (`ttml.rs`, `roxmltree`) gives a line its end, per-word ends, `alt` (the duet's second voice) and `bg` (background vocals); all optional in the schema, so line-timed sources send what they always did. Synced lyrics timed for a recording of another length become plain text (`synced_length_fits`), except a longer recording (`fit_synced_to_song`, lrc.red and LRCLIB): it is taken to be the song with more after it, so the lines that start within the song keep their timing and the rest are dropped, as long as at least half remain; a constant shift is the listener's to fix with the timing offset. Unison answers are checked against the song's title and artist (anyone can submit), and lrc.red documents are only fetched from `https://lrc.red/\u2026ttml`. Better Lyrics' own API is behind Cloudflare Turnstile and is not used. The feature set follows the Better Lyrics extension (GPL-3.0) but none of its code is here: do not copy from it.

Translation and romanization (`translate.rs`; `translate_lyrics` / `romanize_lyrics` bridge commands) go through Google Translate's public web endpoint, per shown line (`shown_lines` = the timed lines, else the plain text's lines; `shownLines` in TS is the same list), are off by default (`lyrics_translate_enabled`, `lyrics_translate_lang`, `lyrics_romanize_enabled`), cached in memory, and a chunk whose answer doesn't come back line for line is left untranslated. A refusal from the endpoint is an ordinary error shown as a toast; never work around it. The two switches under the lyrics save through `set_lyrics_display` (only those two settings) and announce it as `config-updated`, which Settings listens for.

On the page, `src/plugins/lyrics/view.ts` (`LyricsView`) renders one lyrics display and is used twice: in YTM's Lyrics tab and in `fullscreen.ts` (`LyricsFullscreen`), which is our own element shown with the Fullscreen API (the window follows through `windowControls.ts`), not a restyling of YTM's fullscreen player. It is the app's only fullscreen while the lyrics plugin is on: `takeOverFullscreen` catches YTM's `ytmusic-player .fullscreen-button` and its bare-F shortcut in the capture phase, and if YTM's fullscreen comes up another way (`player-ui-state="FULLSCREEN"`) a poll leaves it through YTM's own `.exit-fullscreen-button` and opens ours (checked against the live page). The controls under the lyrics are one row of icon buttons (`buildBar`: source, translate, romanize, timing \u2212 value +, wrong lyrics, search again; the value resets the timing), not chips with labels. The word being sung fills through a `--ytmd-fill` custom property on our own word spans: every word of the sung line is painted by the same gradient (0 = not sung, 1 = sung), written every frame for the word in progress. A line timed only as a whole (LRCLIB and most LRC) gets estimated word timing in the view (`estimateWords`: the words share the time to the next line by length, capped at a plausible singing pace), so every synced song fills; the estimate never leaves the view. Never give a word a second way of being painted (a "sung" class, a color transition): switching between them made every finished syllable blink. Between the player's ticks the position follows the video element's own clock (`carriedPosition`); timed by the wall clock it drifted and each tick snapped the fill forward. Interlude rows stay laid out and only fade, so nothing below them shifts. The looks (`lyrics_theme`; `LYRICS_THEMES` in config.rs and view.ts, a `[data-theme]` block each in styles.ts, an option each in settings.html; a test keeps the four in step) only set the view's custom properties and alignment. `lyrics_effects` (per-line blur, the sung line's scale) defaults to off on Linux: WebKitGTK repaints blurred layers every frame. The fullscreen backdrop is the cover pre-blurred by `renderAmbientWash()`, never a live blur (a test checks the stylesheet). Answers are cached per video id in `~/.oscilla/lyrics_cache/` (30 days, misses 1 day and only when every provider answered, picks kept, 50 MB cap), per-song timing offsets live in `~/.oscilla/lyrics_offsets.json` (imported once from the page's old `ytmd-lyrics-offsets` localStorage). LRC is parsed in Rust (`lrc.rs`, incl. enhanced-LRC word tags). The current song's lyrics are broadcast as `lyrics-changed` and returned by `get_current_lyrics`, both shaped by `schemas/lyrics_v1.json` (a test pins `CurrentLyrics` to it); `src/types/lyrics.ts` holds the TS side and the shared `activeLineIndex`/`activeWordIndex`. A lookup overtaken by a newer song never replaces the current lyrics (`generation`).

### Phone remote
`remote_server.rs` (off by default: `remote_enabled`, bound per `remote_bind` to the LAN address or all interfaces, rate-limited) serves the phone app (`remote.html` + `src/remote/`, its own Vite build `vite.remote.config.ts` → `dist-remote/`, embedded with `rust-embed`; `cargo test` works without it and serves a "not built" page) and a `/ws` WebSocket speaking `schemas/remote_v1.json` (mirrored by `remote_server/protocol.rs` and `src/remote/protocol.ts`; both are tested against the schema, so change all three together and bump the version for a breaking change). Auth: the QR's `/?t=<token>` is swapped once for an `HttpOnly; SameSite=Strict` cookie and a redirect to `/`; requests need that cookie, a `Host` that is an IP literal or `localhost` on our port (blocks DNS rebinding), and a same-origin `Origin` on the socket. The token is kept in `~/.oscilla/remote_token` (0600) so bookmarks survive restarts; `regenerate_remote_token` (Settings → "Revoke paired phones") replaces it and closes every open socket. There is no generic command endpoint any more: the old `/api/invoke` let anything on the LAN with the token start downloads and read the config. Phone actions for the YTM page go out as the `remote-action` event and come back through the `remote_reply` bridge command; while a phone is connected (`remote-clients` event / `remote_clients` command) the page reports what the phone shows through `remote_publish` (`src/plugins/remote/host.ts`). Listen Together actions (react, vote skip, shared-queue edits, enqueue) go straight to `sync_room` in Rust, so the host's role rules apply; a guest's "play" goes through `routeRoomPlayVideo` like any guest pick. The phone's queue edits and enqueue outside a room use YTM's own queue store (`#queue`'s `dispatch` with `SET_INDEX`/`MOVE_ITEM`/`REMOVE_ITEM`/`ADD_ITEMS`, items from `music/get_queue`) and search uses `ytmusic-app`'s `networkManager.fetch('/search')`: the one place Oscilla calls into YTM's JS rather than the DOM, and only through actions YTM's own UI dispatches (the same approach th-ch/youtube-music ships); never write to those objects' state directly. The phone clock is never compared with the desktop's: `state` carries `sampled_at_ms` and `server_time_ms` (both desktop time) and the phone adds only its own elapsed time since receipt.

### Updates
The updater asks `https://kayzedd.github.io/Oscilla/updates/latest.json`. The repo is private, so `.github/workflows/pages.yml` mirrors the newest published release's update files to GitHub Pages (with the join page) when a release is published, rewriting `latest.json` with `scripts/update-manifest.ts`; the app still verifies every file against the minisign updater key built into it (never change that key pair). YTMD 0.2.0 and older still use the Cloudflare Worker (`docs/updates.md`).

### Config
User config is a single JSON file at `~/.oscilla/config.json` (not XDG `~/.config/`), managed by `ConfigManager` in `config.rs`; the frontend reads/writes it through the `get_config`/`save_config` commands via whichever IPC path applies to that window.

## Visual design: looks like YouTube Music made it

Everything Oscilla adds, inside the YTM page and in its own windows, uses YouTube Music's visual language (Roboto, YTM's near-black canvas and #212121 surfaces, white/70%-white text, 40px round icon buttons, 36px pill buttons, 8px-radius chips and inputs, YTM's toggles, sliders, list rows and bottom player bar), speaks the user's language (Polish/English), and sits over a subdued per-track album-art wash whose extracted color is the accent.

### Companion windows
`settings.html`, `sync.html`, `local.html`, `miniplayer.html` share `src/ui/styles.css` (component classes: `.titlebar`, `.icon-btn`, `.btn`/`.btn-filled`/`.btn-tonal`, `.chip`, `.input`/`.select`, `.toggle`, `.range`, `.setting-row`, `.tracks-table`, `.player-bar`, ...; use them, don't add inline styles). Every visible string comes from `src/ui/i18n.ts` (`data-i18n`/`data-i18n-label`/`data-i18n-placeholder` in markup, `tr()` in code); `src/tests/companion_i18n.test.ts` fails on untagged visible text or a key missing from a locale. `initWindowChrome()` (`src/ui/window.ts`) wires translations, window buttons, slider fill (`.range` needs `syncRange()` after setting `.value` from code) and the kit's tooltips. Toasts, tooltips and dialogs are the same kit the injected page uses (`src/preload/ui/kit.ts`). Settings save automatically (debounced) like YTM's own settings; there is no Save button. `src/ui/ambient.ts` (`initAmbientBackdrop()`) sets `--ambient-accent`/`-primary`/`-secondary` and the `#ambient-cover` wash from `track-changed` (plus `get_current_track` on open); the miniplayer is the exception, its cover art *is* the backdrop.

### The injected YouTube Music page — and its one hard rule
`src/plugins/ambient/index.ts` (`AmbientLightingPlugin`) paints a full-bleed blurred cover + veil behind the page (`#ytmd-ambient-backdrop`) — the blur is baked once per track into a small bitmap by `renderAmbientWash()` (`color.ts`, also used by `src/ui/ambient.ts`), never a live CSS `filter: blur()`/animation on a full-window layer, and `backdrop-filter` is limited to the thin nav/player bars: WebKitGTK recomposites both on every frame, which made the whole app stutter, and writes `--ytmd-accent`/`-primary`/`-secondary` onto `<html>` per track. `src/plugins/themes/index.ts` + `presets.ts` (`ThemeEnginePlugin`) switch between exactly two static CSS strings — `AMBIENT_THEME_CSS` and `BASE_THEME_CSS` — keyed **solely** off the Ambient Lighting toggle (`ambient_lighting_enabled` / the `set-ambient-enabled` event). There is no separate theme-preset picker any more; that 8-preset system (and the `theme`/`theme_preset` config fields) was removed. Both CSS strings work by overriding YouTube Music's own CSS custom properties (`--ytmusic-*`, `--yt-sys-color-baseline--*`) — that's the *only* mechanism proven both safe and effective for reskinning the native chrome from outside.

**Do not imperatively mutate style on YouTube Music's own Polymer-templated elements from JS** (`ytmusic-nav-bar`, `#nav-bar-background`, `#player-bar-background`, `tp-yt-paper-slider`, anything under `ytmusic-*`/`tp-yt-*`) — no `el.style.setProperty(...)`, no forced-reflow/repaint tricks, even guarded and infrequent. A `<style>` tag with plain `!important` CSS rules targeting those same selectors is fine (that's how the artwork-protection and slider-color rules in `presets.ts` work, safely, today) — the danger is specifically *direct property writes on the elements themselves*, which fight Polymer's own property-effect system for those nodes. This was tried once (forcing `#nav-bar-background`'s translucency to actually repaint, via `offsetHeight` + an opacity nudge) — it worked visually, verified live in Chrome — and then reliably crashed YouTube Music's own renderer in the real app (`Attempted to assign to readonly property` thrown from `scheduler.js`/`music_polymer_inlined_html.js`, blanking the whole page to black). Reverted in commit `a937b69`. If you need to change something about a native YTM element's appearance, find its CSS custom property and override that on `<html>`/`<body>` — never touch the element's `style` directly.

One consequence: `ytmusic-nav-bar`/`ytmusic-player-bar` don't paint their own visible background at all — the real paint happens on separate `#nav-bar-background`/`#player-bar-background` elements (confirmed via `document.elementsFromPoint()` against a live tab). Declarative `!important` rules targeting those two IDs are currently inert (no visible effect) but harmless; don't "fix" that by reaching for JS.

### Injected UI must look like YouTube Music made it
Every control Oscilla adds inside the YTM page is built from `src/preload/ui/kit.ts` (icon buttons, menu, toast, dialog, tooltip, chip, progress ring) and labelled through `src/preload/ui/i18n.ts` (`t()`, picks Polish/English from YTM's own `<html lang>`). Kit styles resolve colors through YTM's `--yt-sys-color-baseline--*` properties first, so they follow the Ambient/Base theme like YTM's native menus do; sizes mirror YTM (Roboto 14px, 40px round icon buttons, 12px-radius menus, bottom-left toasts above the player bar). Rules: no `alert()`/`confirm()` (they freeze the page), no inline hover handlers or hardcoded zinc/sky colors, announce outcomes with `showToast`, tooltips via `data-ytmd-tooltip` (not `title`), and add every new string to both locales (`src/tests/ui_kit.test.ts` fails on a missing key). The nav-bar entry point is `src/preload/ui/navMenu.ts` (menu + the listening-together chip the sync plugin drives with `setSyncStatus`).
